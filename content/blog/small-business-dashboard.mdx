The most useful dashboard shows the one number the owner needs to make a decision today. Everything else is secondary.

## Start with the decision, not the data

Most dashboard projects start with "what data do we have?" They should start with "what decision are we trying to support?"

A florist needs to know if she can take a large order for next Saturday. A restaurant owner needs to know if Tuesday lunches are worth staying open for. A repair shop needs to know which jobs are overdue and which technician has capacity.

Each of these is a single question. A good first dashboard answers it on the first screen, without scrolling or filtering.

## The trap of completeness

A dashboard with thirty charts is a reporting tool, not a decision tool. When everything is visible, nothing is emphasised. The owner opens it, sees a wall of numbers, and goes back to the spreadsheet or the gut feeling.

Build the smallest thing that changes a decision. You can add more later.

## What to put on the first screen

One primary number. One trend (up or down over the last week or month). One alert (something that needs attention today). A way to drill into the detail if needed.

That's it. Everything else belongs on a second screen that the owner chooses to open.

## The data quality problem

Most small business data is inconsistent. Sales recorded in three different places. Inventory updated manually with delays. Invoices that don't match deliveries.

A dashboard that shows confident numbers from bad data is worse than no dashboard. Before building, spend time understanding where the data actually comes from and how trustworthy it is. Surface data quality problems in the UI — a "last updated" timestamp is a simple start.

## A useful first build

A single screen. The key metric for the week. A comparison to last week. A list of items that need action. A simple filter for time range.

Measure whether the owner actually opens it, and whether it changes what they do. That feedback shapes the second version.
